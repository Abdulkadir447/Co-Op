# Import sample files

Files you can upload in **Import** (the upload icon in the left rail, or
`/import`) to prove the importer works end to end on your machine.

They are the catalogue, customer list and sales history of a Kano staples
wholesaler — Naira prices, +234 numbers, dates inside the last six months, so
Reports and the Day 1 Briefing have something to say right after an import.

Everything here is generated by `make_fixtures.py`; the expected result of each
file is asserted by `backend/tests/test_import_fixtures.py`, which drives the
real `/imports/preview → /imports/map → /imports/validate → /imports/commit`
pipeline. If the importer changes, that suite fails instead of these files
quietly becoming misleading.

## Import in this order

**Customers → Products → Orders.** Sales rows are matched to a customer by
email, then phone, then name; a row whose email matches nobody is *rejected*,
not guessed. Products work the same way (SKU first, then name), and a line
with no price of its own falls back to the catalogue price.

## The files

| File | Rows | What it is for | Expected result |
| --- | --- | --- | --- |
| `customers-clean.csv` | 10 | Canonical Co-op headers | 10 customers created |
| `products-clean.csv` | 12 | Canonical Co-op headers | 12 products created, stock levels set |
| `orders-clean.csv` | 18 lines | Sales history, one row per **line** | 18 orders + 18 line items, ₦3,603,300, 222 units |
| `customers-storefront-export.csv` | 8 | Storefront-style headers, **two rows with no email** | 8 created; the two get placeholder `@imported.coop` addresses |
| `products-messy-export.csv` | 8 | Semicolon-delimited, alias headers (`Item Name`, `Selling Price`, `Qty On Hand`), `₦4,500.00` money | Detected as products, all 8 columns mapped automatically, 8 created |
| `orders-accounting-export.csv` | 12 | **Tab**-delimited accounting export, `Invoice #`, US-style dates, no email column | 12 orders created by name matching |
| `products.xlsx` | 6 | Spreadsheet path | 6 products created |
| `products-with-errors.csv` | 11 | 6 good + 5 bad rows | 6 created; 4 named errors (rows 8–11) + 1 in-file duplicate SKU skipped |
| `orders-with-errors.csv` | 8 | 3 good + 5 bad rows | 3 created; 5 named errors |

The two `-with-errors` files are the interesting ones: they prove a bad row is
**reported by row number** while the good rows still import, instead of the
whole file being rejected. Their bad rows cover, in order:

* `products-with-errors.csv` — no product name · price is `N/A` · required
  price blank · stock column says `eleven` · SKU repeated from an earlier row.
* `orders-with-errors.csv` — impossible date `31/31/2026` · quantity `0` · no
  product name · price `free` · a customer email that does not exist
  (`ghost@example.com`), which is the one error you only see after importing
  customers.

## Two things that surprise people

**`order_id` is an idempotency key, not a grouping key.** Each row becomes one
historic order with one line item; a reference the importer has already seen —
in this file or in an earlier import — is *skipped*, not merged. That is why
`orders-clean.csv` gives each line its own reference (`SO-1042-L1`,
`SO-1042-L2`). Re-uploading the same file therefore creates nothing twice.

**Uploads are capped at 5 MB, and only `.csv` and `.xlsx` are read** (CSV with
`,`, `;`, tab or `|` delimiters, UTF-8 with or without BOM; XLSX reads the
first worksheet only). Anything else is refused before parsing.

## Doing it without the browser

```bash
TOKEN="<your Clerk session token>"
API=http://127.0.0.1:8000
F=samples/imports/products-clean.csv

curl -s -H "Authorization: Bearer $TOKEN" -F "file=@$F" $API/imports/preview
curl -s -H "Authorization: Bearer $TOKEN" -H 'Content-Type: application/json' \
     -d '{"entity":"products","headers":["name","sku","unit_price"],"sample_rows":[["Yam","Y1",4500]]}' \
     $API/imports/map
curl -s -H "Authorization: Bearer $TOKEN" -F "file=@$F" -F 'entity=products' \
     -F 'mapping={"name":"name","sku":"sku","unit_price":"unit_price"}' $API/imports/validate
curl -s -H "Authorization: Bearer $TOKEN" -F "file=@$F" -F 'entity=products' \
     -F 'mapping={"name":"name","sku":"sku","unit_price":"unit_price"}' $API/imports/commit
```

`/imports/validate` never writes; `/imports/commit` is the only endpoint that
does, and it is one transaction — a failure rolls back and leaves nothing
behind.

## Regenerating, and stress-testing

```bash
# rewrite every sample file (README.md is hand-written, nothing else is)
.venv/bin/python samples/imports/make_fixtures.py

# performance run: 2,000 products + 8,000 order lines (gitignored, ~800 KB)
.venv/bin/python samples/imports/make_fixtures.py --rows 2000
```

## Known soft edges

* A **negative stock** value imports as-is — the importer does not second-guess
  an old system's stocktake.
* Customers with no email get `<slug>-<n>@imported.coop`. It is a real
  placeholder you can see and edit, and it must stay a syntactically valid
  address: `.local` and `.invalid` are rejected by the API's own email
  validation and used to break the Customers page after an import.
* Ambiguous matches are refused, never guessed: two customers with the same
  name and no email or phone to tell them apart rejects those rows and tells
  you to add a column.
